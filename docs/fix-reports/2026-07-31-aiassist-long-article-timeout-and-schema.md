# AI Assist 长文章优化超时与格式异常修复复盘

- 日期：2026-07-31
- 模块：博客 / AI 优化 / LLM Provider
- 分类：AI Assist 修复复盘
- 状态：已部署现网

## 问题现象

文章“曾仕强 爱情与婚姻”使用 AI Assist 进行语言润色时，在 55% 的“AI Assist 正在生成优化内容”阶段失败。最初提示为笼统的“AI 生成失败”，重试结果一致。

## 排查结论

### 第一层：固定 60 秒超时

两次失败分别耗时 61.0 秒和 60.7 秒，任务错误码均为 `timeout`。OpenAI 兼容 Provider 将 HTTP 超时硬编码为 60 秒，而该文章正文为 6,335 字，结构化优化无法稳定在 60 秒内完成。

极小的上游探测请求在 3.13 秒内成功，证明密钥、网络和模型服务可用，故障不是认证或整体不可达。

### 第二层：正文优化使用了过重 Schema

将超时扩展后，任务在 182.7 秒收到两次上游 HTTP 200，但初次输出和自动修复输出都没有通过 `BlogOptimizationV1` 校验。

根因是 `scope=body` 的语言润色仍要求模型返回标题、摘要、分类、标签、关键词、声明、警告等完整 18 字段 Schema。正文越长，输出越容易截断、遗漏无关字段或产生格式错误。原固定 2,048 输出 token 也不足以容纳完整长正文。

## 修复内容

### 有界长超时

- 新增 `LLM_CONNECT_TIMEOUT_SECONDS`，默认 10 秒。
- 新增 `LLM_READ_TIMEOUT_SECONDS`，默认 300 秒。
- OpenAI 兼容、Anthropic、Ollama Provider 统一使用可配置超时。
- 不采用无限超时，避免上游半开连接永久占用 Heavy Worker。

### 长正文输出预算

- 新增 `LLM_MAX_OUTPUT_TOKENS`，现网配置为 6,144。
- 博客结构化优化显式使用该输出预算，不再沿用通用的 2,048 token。

### 正文专用 Schema

- 新增 `BlogBodyOptimizationV1`，仅包含：

  - `schema_version`
  - `markdown`

- 当 `scope=body` 时，只要求模型返回完整 Markdown 正文。
- 标题、摘要、分类等未选择字段不再要求生成，也不会进入候选变更。
- 完整优化和元数据优化仍使用原有完整 Schema。

### 错误与日志

- 超时提示改为：`AI Assist 生成超时（已等待 300 秒），请重试、缩小优化范围或改用 Radio`。
- 分别提示限流、Provider 不可用、认证配置异常和结构化输出异常。
- 失败日志增加文章 ID、任务 ID、模型、耗时、正文字符数、输出预算和超时配置。
- 格式诊断只记录错误类型、字段位置、响应长度和是否包含代码围栏，不记录文章正文、模型输出、Token 或密钥。

## 为什么不能无限超时

异步任务不受浏览器请求生命周期限制，但 Worker 仍是有限资源。如果不设置上游读取边界，DNS、网络半开连接或模型服务卡死会永久占用 Heavy Worker，后续所有 LLM 任务持续排队，并且取消与重试难以收敛。

因此采用“短连接超时 + 300 秒长读取超时 + 可重试失败”的方式。异步解决的是客户端等待问题，不等于外部依赖可以无限等待。

## 超长文章边界

300 秒与 6,144 token 已覆盖本次 6,335 字文章。接近系统 200,000 字上限的文章仍不应一次性完整改写；后续应采用按 Markdown 结构分块、逐块生成、逐块校验并最终合并的任务链路。当前保持有界失败，不会无限占用 Worker。

## 回滚方式

1. 回滚 LLM Provider 超时配置、正文专用 Schema 和 Worker 分支。
2. 恢复原 Provider 超时与结构化请求。
3. 执行 `./deploy/scripts/deploy.sh up`。

本次无数据库结构变更，不需要数据库 downgrade。
