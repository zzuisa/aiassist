# 修复复盘：博客优化提交 CSRF 403（2026-08-01）

## 现象

提交博客优化时，浏览器对
`POST /api/v1/posts/62de9f60-fee5-4cb8-bf1a-ef1db4320091/optimize`
收到 `403 Forbidden`。页面表现为优化提交失败，任务没有进入队列。

## 根因

后端的优化接口使用会话绑定的 CSRF 令牌保护不安全方法。前端只在内存中保存 CSRF 令牌；当另一个标签页刷新会话、或刷新令牌轮换后，当前页面仍可能携带旧令牌。后端因此返回稳定的 `csrf_failed` 403。

前端请求封装原先只会对 401 自动刷新会话，对 403 不会识别 CSRF 失败并重试，所以用户直接看到提交失败。

## 修改

- 在 `frontend/src/api/client.ts` 中识别 `403` 且错误码为 `csrf_failed` 的响应。
- 复用已有的并发刷新机制刷新会话并更新内存 CSRF 令牌。
- 对同一请求最多自动重试一次，其他 403 不重试，避免掩盖真实权限或业务错误。
- 新增前端回归测试，覆盖“旧令牌 → 刷新 → 使用新令牌重试”的调用顺序。

发布提交：`2dbaf9d`；发布记录：`2f6681e`。

## 验证

1. 使用已登录会话对目标接口不带 CSRF 令牌提交：返回 `403`，错误码为 `csrf_failed`。
2. 使用刷新后令牌重新提交：返回 `202`，任务 ID 为
   `ee104442-b388-4e99-a80b-dac3d4d5cdf2`。
3. 查询任务：状态为 `waiting_user`、进度 `100`、当前步骤为“待审核”，说明提交和后台生成均已完成。
4. 发布脚本验证通过：前端 Node 24 生产构建、数据库迁移、网关健康检查、fast/heavy worker ping 均成功。
5. `vue-tsc` 类型检查通过。当前宿主机 Node 18 无法启动项目要求 Node 24 的 Vitest；生产构建环境已完成 Node 24 构建验证。

## 日志检索方式

只检索状态、错误码、接口路径和任务状态，不输出 Cookie、令牌或请求体：

```bash
docker compose logs --since=2h --no-color backend nginx \
  | rg 'csrf_failed|/optimize|403|ee104442-b388-4e99-a80b-dac3d4d5cdf2'
```

接口级验证可使用浏览器 Network 面板或经过脱敏的 `curl` 响应，仅保留 HTTP 状态和 Problem Details 的 `code` 字段。

## 遗留风险

- 如果刷新 Cookie 已过期、被撤销或发生刷新令牌重放，自动恢复会失败，用户仍需重新登录。
- 多标签页同时触发刷新时由现有的单次并发刷新 Promise 合并请求；极端网络中断时仍可能需要用户再次提交。
- 本次修复只处理 CSRF 会话同步问题，不改变文章所有权、版本冲突或其他 403/409 业务规则。
