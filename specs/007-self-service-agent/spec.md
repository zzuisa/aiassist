# Feature Specification: 自助式问答与任务执行 Agent

**Feature Branch**: `007-self-service-agent`（本次不新建分支，直接在当前工作目录推进）

**Created**: 2026-08-06

**Status**: Draft

**Input**: User description: "用户可以通过自然语言向系统提出数据查询、内容分析、批量处理、文章管理或系统操作需求。系统理解意图，调用已有 API / MCP 工具 / 多 Agent 能力获取真实数据并完成任务，向前端实时展示 Agent 状态，保留可审计执行记录，写操作需用户确认，能力不足时明确说明而不编造。"

## 概述

当前系统里，"AI 帮我做事"这件事被切成了互不相通的三块：`assistant` 模块只认两种写死的意图（`plan_today`、`adjust_week`），运行记录存在进程内存里；博客优化有一套真正的多 Agent 编排（`editor-agent` / `logic-agent` / `data-agent` / `scene-image-agent` / `illustration-agent`），但只能通过"优化某篇文章"这一个入口触发；`/blog/search`、`/blog/timeline`、`/blog/taxonomy` 等一批只读查询接口存在，但用户必须自己知道点哪个页面。

本特性提供一个统一的自然语言入口：用户说"最近 10 篇文章"、"当前有多少类别"、"给这些文章提取标签"，系统自己判断该调哪些工具、要不要并行、要不要读正文、要不要先请示，然后把过程和结果如实呈现出来。

**明确不做**：不引入反思链、规划树、自动重规划等装饰性推理结构；不为每种问法新造工具；不把编排过程本身变成用户要理解的东西。

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 自然语言查询，只拿必要数据 (Priority: P1)

作为使用者，我用一句话提出查询需求（"给我最近 10 篇文章"、"当前有多少类别的文章"），系统识别意图、调用合适的只读接口、对结果做必要整理，然后只回答我问的东西——标题、链接、标签这类轻量字段，不把正文塞进来，也不把接口原始响应倒给我。

**Why this priority**: 这是整个特性的地基，也是"数据最小化"原则唯一能被独立验证的地方。没有它，后面所有批量处理、多 Agent、写操作都失去了取数基础。它本身即可交付：用户当天就能用自然语言查文章，不必再自己找页面。

**Independent Test**: 提出"给我最近 10 篇文章"，系统返回 10 条含标题与链接的结果；检查本次请求的执行记录，确认调用的是列表类只读接口，且未调用任何正文读取接口、未将正文写入模型上下文。

**Acceptance Scenarios**:

1. **Given** 系统已有文章列表查询能力，**When** 用户提出"给我最近 10 篇文章"，**Then** 系统调用轻量列表接口（按发布时间倒序、限制 10 条），只返回文章 ID、标题、访问链接、分类、标签、发布时间等元数据，不获取正文。
2. **Given** 用户提出"当前有多少类别的文章"，**When** 系统存在聚合统计能力，**Then** 系统调用聚合接口得出分类数与各分类文章数，而不是拉取全部文章再在内存里数。
3. **Given** 查询结果含空分类、重复分类或明显异常值，**When** 系统整理结果，**Then** 系统去空、去重、统一名称格式后再呈现，并对被剔除或标记为异常的数据给出说明。
4. **Given** 用户的需求可以由当前会话上下文完全确定，**When** 系统准备执行，**Then** 系统直接执行，不再追问已经能推断出的条件。
5. **Given** 用户只提了"最近的文章"而未说数量且上下文无法推断，**When** 该条件影响结果正确性，**Then** 系统只就这一个必要条件提问，不附带其他无关澄清。
6. **Given** 只读查询、统计与分析类任务，**When** 系统执行，**Then** 不要求用户额外确认。

---

### User Story 2 - 实时看见谁在干什么 (Priority: P1)

作为使用者，任务执行期间我能在前端持续看到：当前在跑哪个 Agent、它负责什么、正在做哪一步、用的哪个工具、什么状态、进度到哪了。任务结束后我能看到结果摘要或失败原因。

**Why this priority**: 与 US1 并列 P1，因为长任务如果没有可见状态，用户只能盯着转圈猜，与现有 Job 中心的体验割裂。这一条独立可测：即便只有单 Agent 查询，状态事件也应完整走通。

**Independent Test**: 触发一次任意查询，订阅状态通道，验证至少收到一次 `running` 事件与一次终态事件，且事件中 Agent 名称、职责、当前任务、工具名、状态、进度字段完整。

**Acceptance Scenarios**:

1. **Given** 一个任务开始执行，**When** 任一 Agent 启动、更新或结束，**Then** 系统发出一条状态事件，包含 `task_id`、`agent_id`、`agent_name`、`responsibility`、`current_task`、`status`、`current_tool`、`progress`、`result_summary`、`error_message`、`started_at`、`finished_at` 与事件时间戳。
2. **Given** 状态字段，**When** 前端消费事件，**Then** `status` 取值限定为 `pending`、`running`、`waiting_confirmation`、`success`、`partial_success`、`failed`、`skipped` 之一。
3. **Given** 任务总量可以确定（如 25 篇文章），**When** 处理进行中，**Then** 进度以 `current`/`total` 表达，并随处理推进更新。
4. **Given** 任务总量无法预先确定，**When** 处理进行中，**Then** 系统提供当前阶段的文字描述而不是伪造的进度数字。
5. **Given** 任一状态事件，**When** 生成事件内容，**Then** 事件中不包含模型内部思维过程、隐藏推理链、完整系统提示词，也不包含密钥、令牌、密码、Cookie 或认证头。
6. **Given** 多个 Agent 并行运行，**When** 用户查看前端，**Then** 每个 Agent 各自独立呈现名称、职责、当前任务、状态与进度，可区分而不混淆。

### User Story 3 - 按需读正文，批量任务并行处理 (Priority: P2)

作为使用者，当我要求总结、优化、提取标签关键词或对比多篇文章时，系统才去读取相应正文；文章数量较多时，系统复用已有的多 Agent 能力并行处理，并把结果汇总成一份可读的交付物。

**Why this priority**: 这是本特性的主要产能来源，但依赖 US1 建立的取数与范围确定能力，因此排在 P1 之后。它独立可测：给定一批文章 ID，批量提取标签这条链路可以单独验收。

**Independent Test**: 对 US1 查到的 10 篇文章提出"提取标签和关键词"，验证系统只读取这 10 篇的正文、按批分配给多个内容分析 Agent 并行执行、最终返回去重且格式统一的标签集合，并明确区分已生成/已保存/失败/未处理。

**Acceptance Scenarios**:

1. **Given** 用户要求总结、优化、分析、提取标签关键词或对比文章内容，**When** 系统执行，**Then** 系统才调用正文读取能力，且只读取目标文章。
2. **Given** 用户只是要求展示文章列表，**When** 系统执行，**Then** 系统不批量加载正文。
3. **Given** 待处理文章数量较多且子任务彼此独立，**When** 系统规划执行，**Then** 系统复用现有多 Agent 并行能力，按合理批次分配。
4. **Given** 任务是单篇查询、简单分类统计或单接口即可完成的请求，**When** 系统规划执行，**Then** 系统使用单 Agent，不创建多个 Agent。
5. **Given** 创建了多个子 Agent，**When** 分配任务，**Then** 每个子 Agent 具备 `agent_id`、`agent_name`、`responsibility`、`current_task`、`input_scope`、`allowed_tools`、`expected_output`、`allow_write`、`status`，且不同 Agent 不重复处理同一批数据（除非任务明确要求交叉校验）。
6. **Given** 各子 Agent 返回结果，**When** 主控 Agent 汇总，**Then** 系统执行去重、格式统一与质量检查，并明确区分"已生成未保存""已成功保存""保存失败""未处理"四种状态。
7. **Given** 部分子 Agent 失败，**When** 汇总结果，**Then** 已成功部分被保留，失败项与原因单独列出，不因个别失败丢弃全部成果。

### User Story 4 - 写操作先说清楚再动手 (Priority: P2)

作为使用者，系统在修改、创建、删除、发布或批量更新我的数据之前，先告诉我准备改什么、影响多少条、改动范围、能否回滚、生成结果是否可预览；我确认之后它才动手。

**Why this priority**: 直接对应宪法"人类权威与可逆自动化"原则，是本特性能否被信任的前提。依赖 US3 产出待写入的结果，故排 P2。

**Independent Test**: 在批量提取标签后要求"保存到系统"，验证系统先给出影响范围说明并进入 `waiting_confirmation` 状态且不写入任何数据；确认后才执行写入并给出成功/失败明细。

**Acceptance Scenarios**:

1. **Given** 待执行操作属于更新、创建、删除、发布、回滚、批量修改或修改系统配置，**When** 系统准备执行，**Then** 系统先说明修改内容、预计影响条数、修改范围、是否支持回滚、生成结果是否可预览，并将相关 Agent 置为 `waiting_confirmation`。
2. **Given** 系统正在等待确认，**When** 用户尚未确认，**Then** 系统不执行任何写入。
3. **Given** 用户明确确认，**When** 系统执行写入，**Then** 写入通过既有领域服务完成，重新校验归属与版本，并返回成功、失败与未处理的明细。
4. **Given** 用户在原始请求中已明确要求执行且系统规则允许直接执行，**When** 操作不属于高风险类别，**Then** 可视为已确认。
5. **Given** 操作属于删除、覆盖或批量更新等高风险类别，**When** 即便原始请求已表达执行意图，**Then** 系统仍再次确认。
6. **Given** 系统只具备读取能力而缺少对应写入能力，**When** 用户要求保存结果，**Then** 系统明确说明"可以生成但无法写回"，展示结果供用户自行处置，且不谎称已保存。

### User Story 5 - 每一步都留痕且可审计 (Priority: P3)

作为系统维护者，我可以查看任一次任务的完整执行记录：调用了哪些工具、参数摘要、返回规模、每步状态、耗时、失败原因，并确认记录中不含任何凭据。

**Why this priority**: 对应宪法"可观测与可追溯"原则。它是运维与纠纷排查能力，不阻塞用户主流程，故排 P3。

**Independent Test**: 执行一次含失败步骤的批量任务，导出执行记录，验证每次工具调用都有独立条目且字段完整，并检索记录全文确认不含密码、令牌、API Key、Cookie、认证头或私钥。

**Acceptance Scenarios**:

1. **Given** 系统调用任一 API、工具或子 Agent，**When** 调用发生，**Then** 生成一条执行记录，含 `task_id`、`step_id`、`agent_id`、`agent_name`、执行步骤、工具或接口名称、操作类型、请求参数摘要、返回数量或结果摘要、执行状态、错误原因、开始时间、完成时间与执行耗时。
2. **Given** 执行记录的操作类型字段，**When** 记录生成，**Then** 取值限定为 `query`、`analyze`、`create`、`update`、`delete`、`publish`、`rollback` 之一。
3. **Given** 请求参数中含敏感值，**When** 写入执行记录，**Then** 敏感参数被脱敏，记录中不出现密码、令牌、API Key、Cookie、完整认证头或私钥。
4. **Given** 一次任务包含多个步骤，**When** 用户或维护者查看记录，**Then** 步骤可按执行顺序还原，且能区分成功、失败与跳过。

---

### User Story 6 - 多轮对话里"这些"指的是刚才那些 (Priority: P3)

作为使用者，我先说"获取最近 10 篇文章"，再说"给这些文章提取标签"，系统知道"这些"是刚才那 10 篇，而不是全库文章。

**Why this priority**: 显著提升连续使用体验，但单轮明确指令下功能仍可用，故排 P3。

**Independent Test**: 连续两轮对话，第二轮使用指代词，验证系统处理的对象 ID 集合与第一轮返回结果完全一致，且未扩大到全量数据。

**Acceptance Scenarios**:

1. **Given** 上一轮返回了一批对象，**When** 用户在下一轮使用"这些""它们"等指代，**Then** 系统将范围限定为上一轮的对象集合。
2. **Given** 会话进行中，**When** 系统维护上下文，**Then** 保留上一轮对象 ID、查询条件、查询范围、排序方式、用户已确认的操作、尚未执行的写操作，以及已完成与已失败的对象。
3. **Given** 上一轮数据已过期、对象已变化或范围不明确，**When** 用户发出后续指令，**Then** 系统重新查询并向用户说明范围已刷新。
4. **Given** 某些对象在上一轮已成功处理，**When** 用户重复发出同一指令，**Then** 系统不重复执行已成功完成的步骤。

---

### User Story 7 - 做不到就说做不到 (Priority: P3)

作为使用者，当系统缺少接口、字段、权限或数据时，我得到的是一份清楚的能力说明，而不是一个看起来很像真的但其实编出来的答案。

**Why this priority**: 是贯穿全部故事的安全底线，但作为独立交付物它更接近"验收护栏"，故单列 P3 便于专门验收。

**Independent Test**: 提出一个当前系统确实不具备对应接口的请求，验证系统拒绝编造、明确列出缺失能力，并给出可完成与不可完成部分的划分。

**Acceptance Scenarios**:

1. **Given** 没有能完成任务的工具，**When** 系统响应，**Then** 系统说明缺少什么能力、缺少什么接口/字段/权限、当前可完成哪部分、不可完成哪部分、推荐补充什么能力。
2. **Given** 某接口不存在，**When** 系统规划执行，**Then** 系统不声称调用了它，也不根据接口名称猜测其返回内容。
3. **Given** 工具调用失败，**When** 系统响应，**Then** 系统不使用模拟数据代替真实结果。
4. **Given** 任务部分成功，**When** 系统汇报，**Then** 系统不将部分成功描述为全部成功，也不隐藏失败项。

---

### Edge Cases

- 用户一次请求的对象数量远超单次处理能力（例如"给全部文章提取标签"）时，系统如何界定批次上限并向用户说明实际处理范围？
- 工具调用失败时如何区分参数错误、网络错误、权限错误、数据不存在、接口能力不足与系统内部错误？在何种情况下自动重试一次是安全且有意义的？
- 重试仍失败时，如何停止当前相关步骤而不中断其他独立 Agent 的执行？
- 并行 Agent 之间出现结果冲突（同一文章被赋予不一致标签）时，主控 Agent 依据什么规则裁决？
- 用户在系统处于 `waiting_confirmation` 期间发出新的无关请求，原待确认操作如何处置？
- 写入过程中途失败，已写入部分与未写入部分如何呈现，是否需要提供回滚入口？
- 上一轮范围内的文章在本轮执行前被其他会话修改或删除，系统如何检测并处理？
- ~~状态事件通道断开后重连，前端如何恢复到当前真实状态而不丢失中间进度？~~ → 已由既有 SSE 的 `Last-Event-ID` 重放 + 快照重同步机制解决，本特性只需扩展快照负载使其包含在跑的 Agent（见 research.md R-003）。
- 用户请求本身表述模糊到无法归入任何已知意图类别时的兜底行为。

## Requirements *(mandatory)*

### Functional Requirements

**意图识别与范围确定**

- **FR-001**: 系统 MUST 结合用户当前问题与会话上下文，将请求归入数据查询、列表检索、聚合统计、内容分析、单篇文章优化、批量文章处理、数据创建、数据更新、数据删除、发布/回滚或其他系统任务之一。
- **FR-002**: 当需求可由现有上下文确定时，系统 MUST NOT 重复询问。
- **FR-003**: 仅当缺少关键条件、且该条件无法通过工具或上下文获得时，系统 MAY 提问，且 MUST 只问完成任务所必需的问题。

**工具选择**

- **FR-004**: 系统 MUST 在执行前检查当前可用的 API、工具与 Agent 能力，并选择能完成任务的最少工具组合。
- **FR-005**: 系统 MUST NOT 将单个工具即可完成的任务拆成多个无意义步骤，MUST NOT 调用与当前任务无关的接口，MUST NOT 重复获取已存在且仍有效的数据。
- **FR-006**: 系统 MUST NOT 声称调用不存在的接口、根据接口名称猜测返回内容、编造工具执行结果或以模拟数据代替真实数据。
- **FR-007**: 当没有合适工具时，系统 MUST 输出结构化的能力缺口说明（缺失能力、缺失接口/字段/权限、可完成部分、不可完成部分、建议补充项）。

**数据最小化**

- **FR-008**: 对文章列表类请求，系统 MUST 只获取与展示轻量字段（文章 ID、标题、访问链接、分类、标签、关键词、发布时间、更新时间、状态）。
- **FR-009**: 对文章列表类请求，系统 MUST NOT 主动获取文章正文，也 MUST NOT 将正文载入模型上下文。
- **FR-010**: 系统 MUST 仅在总结、优化重写、内容分析、标签/关键词提取、多篇内容比较或任务明确依赖正文时才读取正文，且只读取目标文章。
- **FR-011**: 已存在聚合统计能力时，系统 MUST 优先调用聚合接口，MUST NOT 为统计数量而拉取全部文章正文。

**多 Agent 调度**

- **FR-012**: 系统 MUST 在任务彼此独立可并行、处理对象数量较大、子任务需要不同专业能力、并行能明显缩短时间或用户明确要求时，才使用多 Agent。
- **FR-013**: 系统 MUST 对单接口可完成、数据量小或多 Agent 无明显收益的任务使用单 Agent。
- **FR-014**: 每个子 Agent MUST 携带 `agent_id`、`agent_name`、`responsibility`、`current_task`、`input_scope`、`allowed_tools`、`expected_output`、`allow_write`、`status`。
- **FR-015**: 多个 Agent MUST NOT 重复处理同一批数据，除非任务明确要求交叉校验。
- **FR-016**: 主控 Agent MUST 负责需求理解、拆分判断、任务分配、并发控制、结果汇总、去重与质量检查、部分失败处理与最终结论输出。
- **FR-017**: 系统 MUST 复用既有 Agent 类型（主控、文章查询、内容分析、数据操作），MUST NOT 为每种用户问法新造 Agent 类型或新造工具。

**数据处理**

- **FR-018**: 系统 MUST 对工具返回结果按任务需要执行去空值、去重、名称格式统一、明显相同项合并、统计合理性检查与异常数据标记。
- **FR-019**: 系统 MUST 保留文章 ID 等必要对象标识，MUST 区分原始数据与 AI 生成结果，MUST NOT 擅自修改原始业务数据。
- **FR-020**: 系统 MUST NOT 将接口原始响应整体展示给用户，只展示对当前目标有价值的信息。

**写操作确认**

- **FR-021**: 系统 MUST 在执行更新、创建、删除、发布、回滚、批量修改或修改系统配置前，说明修改内容、预计影响条数、修改范围、是否支持回滚与结果可预览性，并等待用户确认。
- **FR-022**: 只读查询、统计与分析 MUST NOT 要求额外确认。
- **FR-023**: 用户原始请求已明确要求执行且系统规则允许时，MAY 视为已确认；但删除、覆盖、批量更新等高风险操作 MUST 再次确认。
- **FR-024**: 写入 MUST 通过既有领域服务执行，重新校验归属与版本约束。

**状态反馈**

- **FR-025**: 系统 MUST 在任一 Agent 启动、更新或结束时发出状态事件，字段见 US2 场景 1。
- **FR-026**: `status` MUST 限定为 `pending`、`running`、`waiting_confirmation`、`success`、`partial_success`、`failed`、`skipped`。
- **FR-027**: 总量可确定时进度 MUST 以 `current`/`total` 表达；不可确定时 MUST 以阶段描述代替，MUST NOT 伪造进度数字。
- **FR-028**: 状态反馈 MUST NOT 包含模型内部思维过程、隐藏推理链、完整系统提示词、未经验证的推测，或密钥、令牌、密码与认证信息。

**执行留痕**

- **FR-029**: 每次 API、工具或子 Agent 调用 MUST 生成执行记录，字段见 US5 场景 1。
- **FR-030**: 操作类型 MUST 限定为 `query`、`analyze`、`create`、`update`、`delete`、`publish`、`rollback`。
- **FR-031**: 执行记录 MUST NOT 保存或展示密码、令牌、API Key、Cookie、完整认证头、私钥或其他敏感数据；敏感参数 MUST 脱敏。

**失败处理**

- **FR-032**: 工具调用失败时系统 MUST 判定失败类型（参数错误、网络错误、权限错误、数据不存在、接口能力不足、系统内部错误）。
- **FR-033**: 在安全且有意义时系统 MAY 自动重试一次；重试仍失败 MUST 停止当前相关步骤，且 MUST NOT 影响其他独立 Agent 继续执行。
- **FR-034**: 已成功完成的部分 MUST 保留；最终结果 MUST 区分全部成功、部分成功与全部失败，并说明失败步骤与原因。

**多轮上下文**

- **FR-035**: 系统 MUST 保留当轮会话的业务上下文（上一轮对象 ID、查询条件、范围、排序方式、已确认操作、未执行写操作、已完成与已失败对象）。
- **FR-036**: 上一轮数据过期、对象变化或范围不明确时，系统 MUST 重新查询并向用户说明。
- **FR-037**: 系统 MUST NOT 重复执行已成功完成的步骤。

**输出格式**

- **FR-038**: 普通查询任务的回复 MUST 采用「处理结果 / 执行记录 / 局限说明」结构，其中局限说明仅在数据缺失、权限不足、能力不足、部分失败或数据可能不完整时出现。
- **FR-039**: 任务执行类请求的回复 MUST 采用「执行计划 / 当前运行 Agent / 执行结果 / 执行记录」结构。
- **FR-040**: 输出 MUST NOT 包含正文、数据库字段、完整接口响应、工具内部参数、不相关时间字段或 Agent 内部分析过程，除非用户明确要求查看详情。

**工具注册与 MCP 约束（源自 D-001 / 宪法 1.1.0）**

- **FR-041**: 所有 Agent 工具调用（含 MCP 暴露的工具）MUST 经由类型化工具注册表，具备可替换提供方、超时、有界重试、用量日志与稳定领域错误。
- **FR-042**: 只有安全清单字段（工具名、类型、职责、所需权限、可用状态）MAY 进入模型提示词或用户可见界面；端点、凭据、令牌与连接串 MUST NOT 出现在提示词、状态事件或执行记录中。
- **FR-043**: 每次工具调用 MUST 强制调用者的归属范围，并 MUST 产生参数脱敏后的审计记录。
- **FR-044**: 未在注册表中登记的工具 MUST NOT 被描述为可调用，其结果 MUST NOT 被模拟。

**与 spec 006 的边界（源自 D-002）**

- **FR-045**: Agent 的身份、职责、可编辑文案与关联能力 MUST 来自 spec 006 的配置，本特性 MUST NOT 另建 Agent 定义模型。
- **FR-046**: 启动 Agent 时 MUST 绑定其在 006 中的当时生效版本，并在状态事件与执行记录中记录该版本标识；006 的后续版本变更 MUST NOT 影响已在运行的任务。
- **FR-047**: 006 中标记为不可用、停用或未注册的 Agent 与能力，MUST 被视为不可调用并触发能力缺口说明，MUST NOT 降级为伪执行。

**assistant 模块吸收与去硬编码（源自 D-003）**

- **FR-048**: 意图 MUST NOT 以硬编码分支实现；新增意图 MUST NOT 要求修改核心调度代码。
- **FR-049**: 任务、运行实例、状态与执行记录 MUST 持久化，MUST NOT 依赖进程内存；进程重启后 MUST 可恢复查询。
- **FR-050**: 现有"今日安排建议"与"周计划调整"能力 MUST 在新体系下作为普通意图继续可用，且 MUST 保留既有保障：动作卡片引用真实实体 ID 与版本、应用动作时经既有领域服务重新校验归属与乐观版本、固定事件不被 AI 移动。
- **FR-051**: 现有 assistant 对外接口契约的变更 MUST 在 plan 阶段给出迁移方式（替换或兼容层），MUST NOT 静默破坏既有前端调用。

### Key Entities

- **AgentTask（任务）**: 一次用户请求对应的顶层执行单元。关键属性：`task_id`、发起用户、原始请求、识别出的意图类别、整体状态、创建与完成时间、最终结论摘要。一个任务包含多个 AgentRun 与多条 ExecutionRecord。
- **AgentRun（Agent 运行实例）**: 任务内一个 Agent 的一次运行。关键属性：`agent_id`、`agent_name`、`responsibility`、`current_task`、`input_scope`、`allowed_tools`、`expected_output`、`allow_write`、`status`、`current_tool`、进度、开始/完成时间、结果摘要、错误信息。归属于一个 AgentTask，可有父子关系（主控与子 Agent）。
- **ExecutionRecord（执行记录）**: 一次工具/接口/子 Agent 调用的审计条目。关键属性：`task_id`、`step_id`、`agent_id`、`agent_name`、执行步骤、工具名称、操作类型、脱敏后参数摘要、结果摘要、状态、错误原因、开始/完成时间、耗时。
- **ToolManifest（工具清单）**: 当前可供 Agent 选择的能力目录。关键属性：工具名、类型（只读/写入）、职责描述、所需权限、可用状态。仅暴露安全清单字段，不含端点凭据。
- **ConversationScope（会话范围）**: 支撑多轮指代的上下文。关键属性：上一轮对象 ID 集合、查询条件、排序方式、已确认操作、待执行写操作、已完成与已失败对象、范围有效性标记。
- **PendingWrite（待确认写操作）**: 生成完毕但尚未落库的变更。关键属性：目标对象集合、变更内容预览、预计影响条数、是否可回滚、生成时间、确认状态。

### Data Safety & AI Control *(mandatory when the feature stores content or uses AI)*

- **Durable acceptance point**: 用户内容在通过既有领域服务写入数据库并提交事务后视为已保存。AI 生成的标签、关键词、正文改写在用户确认前一律是"已生成未保存"的提案，不进入业务状态。任务与执行记录在任务创建时即持久化，不依赖 AI 调用成功。
- **AI authority boundary**: AI 可自主执行只读查询、统计与分析。所有更新、创建、删除、发布、回滚与批量修改必须先呈现影响范围并获得用户确认；删除、覆盖、批量更新即便用户已在原始请求中表达意图，仍需再次确认。AI 不得修改原始业务数据，AI 生成结果必须与用户原有数据可区分。
- **Failure fallback**: 模型、工具或消息队列不可用时，用户原有文章与数据保持完整可访问；已成功完成的步骤结果保留；任务转为部分成功状态并列出失败项与原因，而非整体回滚或以模拟数据填充。工具不存在时明确报告能力缺口，绝不伪造调用。
- **Privacy and ownership**: 所有查询与变更强制归属过滤，用户只能操作自己的对象。执行记录与状态事件中的敏感参数一律脱敏，不含密码、令牌、API Key、Cookie、认证头与私钥。状态事件不外泄系统提示词与模型内部推理。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 对"获取最近 N 篇文章"类请求，系统返回结果中正文字段占比为 0%，且执行记录显示未调用任何正文读取接口。
- **SC-002**: 用户从提出自然语言查询到看到第一条 Agent 状态事件的时间不超过 2 秒。
- **SC-003**: 单接口可完成的简单查询中，创建的 Agent 数量为 1 的比例不低于 95%。
- **SC-004**: 所有写操作在执行前均产生一次可见的确认环节，未确认即写入的发生次数为 0。
- **SC-005**: 任意一次任务的执行记录可完整还原全部工具调用步骤，步骤缺失率为 0%。
- **SC-006**: 对执行记录与状态事件的全量检索中，出现密码、令牌、API Key、Cookie、认证头或私钥的条目数为 0。
- **SC-007**: 系统不具备对应能力的请求中，返回结构化能力缺口说明而非编造结果的比例为 100%。
- **SC-008**: 批量任务中部分子任务失败时，已成功部分的结果保留率为 100%，且最终汇报明确区分成功/失败/未处理三类。
- **SC-009**: 连续两轮对话中使用指代词的场景，系统处理对象集合与上一轮返回集合完全一致的比例不低于 95%。
- **SC-010**: 25 篇文章的批量标签提取任务，采用并行处理后的端到端耗时相比串行处理下降不低于 50%。（达成前提：`worker-heavy` 当前为单并发且与语音/图片共享槽位，需按 research.md R-001 的线程池扇出方案落地，否则该指标不可达成。）

## Assumptions

- 沿用既有 Cookie 认证与 CSRF 机制，本特性不引入新的认证方式；所有查询与变更继承现有归属校验。
- 复用既有异步任务与 SSE 状态通道承载 Agent 状态事件，不引入 WebSocket 或 GraphQL（受宪法"REST 为同步边界、SSE 为单向任务状态通道"约束）。
- 复用 `posts/orchestrator.py` 中既有的 Agent **选择与门控逻辑**（价值评分、能力可用性检查、跳过原因码）。但**并行执行器需新建**：经 Phase 0 核查，现有"多 Agent"实为单次 LLM 调用内的提示词角色组合，并非真并行；`max_agent_calls` 是提示词成本闸门而非并发度，不可直接当并发上限沿用（见 research.md R-000）。
- MCP 工具调用已由宪法 1.1.0 解除延后，但须落在类型化工具注册表之内（见 D-001）；本特性不假定任何特定 MCP 服务端实现。
- 复用既有只读查询接口（文章列表检索、分类/标签统计、时间线等）作为查询类工具来源，本特性不新增业务查询能力。
- 现有 `assistant` 模块由本特性吸收替换（见 D-003），不保留并存；其两个既有能力以普通意图形式继续提供。
- 文章相关的具体工具名称（如 `search_articles`、`get_article_detail`、`update_article_metadata` 等）以系统实际注册的接口为准，规格中不锁定名称。
- 用户为单人自托管场景，并发任务数量有限，不需要跨用户的任务队列隔离设计。

## 已决策事项

以下问题已在规格阶段确认，直接作为 plan 阶段的输入约束：

### D-001：MCP 已解除延后，但受强约束（宪法 1.1.0）

宪法已由 1.0.0 修订至 **1.1.0**，将 MCP 从"explicitly deferred"列表中移除，同时新增绑定性的 Agent 工具调用条款。本特性的工具调用因此 MUST 满足：

- 所有 Agent 工具调用（含 MCP 暴露的工具）经由**类型化工具注册表**，套用 Principle IV 的网关规则：可替换提供方、超时、有界重试、用量日志、稳定领域错误。
- 只有**安全清单字段**（工具名、类型、职责、所需权限、可用状态）可进入模型提示词或用户可见界面。端点、凭据、令牌、连接串 MUST NOT 出现在提示词、状态事件或执行记录中。
- 每次工具调用 MUST 强制调用者的归属范围，并 MUST 产生参数脱敏后的审计记录。
- 未注册的工具 MUST NOT 被描述为可调用，其结果 MUST NOT 被模拟。

对应新增需求见 FR-041 ~ FR-044。

### D-002：006 管配置，007 管运行

spec 006「博客 Agent 内容管理」是 Agent 定义的**唯一权威来源**（身份、职责、可编辑文案、Prompt、关联 Skill 与能力、版本）。本特性 **消费** 006 的配置，MUST NOT 另建一套 Agent 定义模型。

- 007 启动某 Agent 时，MUST 绑定 006 中该 Agent 当时的**生效版本**，并在执行记录与状态事件中记录所绑定的版本标识。
- 006 中的版本变更 MUST NOT 影响已在运行的任务；运行中与历史任务继续使用提交时固定的版本（与 006 既有语义一致）。
- 006 中标记为不可用、停用或未注册的 Agent/能力，007 MUST 视为不可调用，并按 US7 输出能力缺口说明，MUST NOT 降级为"假装执行"。
- 007 只负责**运行期**概念：任务、运行实例、状态事件、执行记录、会话范围、待确认写操作。

对应新增需求见 FR-045 ~ FR-047。

### D-003：吸收并重构现有 assistant 模块，拒绝硬编码

现有 `assistant` 模块的 `plan_today` / `adjust_week` 两个**硬编码意图**与**进程内存态** run 存储（`_RUNS: dict`）由本特性**吸收替换**，不保留并存。

- 意图 MUST NOT 以硬编码分支实现；意图识别 MUST 基于可扩展的意图分类，新增意图 MUST NOT 要求修改核心调度代码。
- 运行状态 MUST 持久化，MUST NOT 依赖进程内存；进程重启后任务、状态与执行记录 MUST 可恢复查询。
- 现有 assistant 的两个能力（今日安排建议、周计划调整）MUST 作为普通意图在新体系下继续可用，其既有保障 MUST 保留：动作卡片引用真实实体 ID 与版本、应用动作时经既有领域服务重新校验归属与乐观版本、固定事件不被 AI 移动。
- 现有 `POST /assistant/runs`、`GET /assistant/runs/{id}`、`POST /assistant/runs/{id}/actions/{action_id}` 的对外契约变更 MUST 在 plan 阶段明确迁移方式（替换或兼容层），MUST NOT 静默破坏既有前端调用。

对应新增需求见 FR-048 ~ FR-051。
