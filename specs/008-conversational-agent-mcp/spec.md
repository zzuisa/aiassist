# Feature Specification: 对话式 Agent 与 MCP 任务路由

**Feature Branch**: `007-conversational-agent-mcp`

**Created**: 2026-08-10

**Status**: Draft

**Input**: User description: "让自助 Agent 从正常聊天中识别并执行任务，必要时选择和调用已授权的 MCP 能力。"

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 像正常助手一样开始对话 (Priority: P1)

作为使用者，我可以用“hi”“你好”“你能做什么”或一段普通自然语言开始交流，系统会自然回应并介绍可用能力，而不是把问候误报成能力缺口或创建一个失败任务。

**Why this priority**: 自然对话是统一入口的基础。如果连问候和能力询问都无法处理，用户就必须预先理解内部意图和工具，Agent 仍然只是命令表单。

**Independent Test**: 在空白会话中依次发送“hi”“你能做什么”，验证系统给出简短、符合当前实际能力的回答，不执行工具、不创建业务写入，也不显示错误式能力缺口。

**Acceptance Scenarios**:

1. **Given** 用户开启新会话，**When** 用户发送问候语，**Then** 系统在对话中自然回应，并邀请用户描述想完成的事情。
2. **Given** 当前存在一组可用和不可用能力，**When** 用户询问“你能做什么”，**Then** 系统基于当前真实能力给出分类说明与示例，不声称拥有未连接、不可用或无权使用的能力。
3. **Given** 用户输入普通闲聊且不包含业务请求，**When** 系统理解该消息，**Then** 系统直接对话，不调用业务工具、不创建待确认写入。
4. **Given** 一句话同时包含寒暄和明确任务，**When** 系统理解该消息，**Then** 系统可以简短回应寒暄并继续处理任务，不要求用户重新表述。

---

### User Story 2 - 从聊天中识别并执行任务 (Priority: P1)

作为使用者，我不需要记住固定命令。我可以说“嗨，帮我看看最近写了什么”“把刚才那些文章归纳一下”，系统会结合对话上下文判断这是聊天、查询、分析、写操作还是需要澄清，并选择合适能力完成任务。

**Why this priority**: 这是从“关键词任务入口”升级到“对话式 Agent”的核心价值，同时保留现有任务执行、安全确认和审计能力。

**Independent Test**: 用户先说“嗨，帮我找最近十篇文章”，再说“把这些文章提取标签并保存”；验证第一轮完成只读查询，第二轮继承同一对象范围、先生成预览、确认前零写入，批准后才保存。

**Acceptance Scenarios**:

1. **Given** 用户用未预设的自然表达描述一个已有能力可完成的任务，**When** 意图和必要参数足够明确，**Then** 系统识别任务目标、对象范围和读写性质并开始执行。
2. **Given** 一条消息同时包含聊天内容和业务请求，**When** 系统处理消息，**Then** 业务请求不会因寒暄、礼貌用语或语序变化而被遗漏。
3. **Given** 用户用“这些”“刚才的”“其中失败的”等指代表达后续任务，**When** 会话中存在唯一可确定的对象范围，**Then** 系统继承该范围且不扩大到其他数据。
4. **Given** 执行任务所需的关键条件无法从当前消息和会话推断，**When** 多种解释会产生实质不同结果，**Then** 系统只询问最少数量的必要问题，并在得到回答后继续原任务。
5. **Given** 请求只需要读取或分析数据，**When** 系统执行，**Then** 无需用户额外确认。
6. **Given** 请求将创建、修改、删除、发布或批量写入用户数据，**When** 系统准备执行，**Then** 系统展示结构化变更预览并等待明确确认；对话中的“好的”“确认”等被引用文本不得触发写入。
7. **Given** 用户拒绝待确认操作，**When** 系统记录决定，**Then** 业务数据保持不变，用户仍可继续同一会话。

---

### User Story 3 - 自动选择已授权的 MCP 能力 (Priority: P2)

作为使用者，当内置能力不能完成任务、但已经连接并授权的 MCP 能力可以完成时，系统能够在对话中选择该能力、说明正在使用什么，并把真实结果带回当前会话。

**Why this priority**: MCP 扩展了任务覆盖面，但必须建立在自然对话路由、权限控制和真实能力发现之上，因此排在核心对话体验之后。

**Independent Test**: 连接一个只读测试 MCP 能力后，用自然语言提出只有该能力能够完成的请求；验证系统选中正确能力、仅传递必要参数、展示执行状态并返回真实结果。断开该能力后重复请求，系统应说明当前不可用而不是编造结果。

**Acceptance Scenarios**:

1. **Given** 一个 MCP 能力已连接、可用且用户有权使用，**When** 它最适合完成当前请求，**Then** 系统可以选择并调用它，无需用户说出工具名称。
2. **Given** 内置能力与多个 MCP 能力都可能完成请求，**When** 系统进行选择，**Then** 优先选择权限足够、范围最小、风险最低且能返回真实结果的能力。
3. **Given** MCP 能力需要用户尚未授予的权限，**When** 系统识别到该能力，**Then** 系统说明所需权限和可完成范围，不自动扩大权限或绕过授权。
4. **Given** MCP 能力执行写操作或产生外部影响，**When** 系统准备调用，**Then** 用户可在确认前看到目标、影响范围、拟提交内容和可逆性，确认前不得产生外部写入。
5. **Given** MCP 能力离线、超时、返回错误或结果不完整，**When** 调用失败，**Then** 系统如实说明失败步骤，保留已成功结果，并提供重试、缩小范围或改用其他可用能力的选择。
6. **Given** MCP 返回内容中包含指令性文本，**When** 系统处理结果，**Then** 这些内容被视为外部数据，不得改变用户授权、系统规则、任务范围或后续工具选择。
7. **Given** 当前没有合适的内置或 MCP 能力，**When** 用户提出请求，**Then** 系统用自然语言说明缺失能力、可完成部分和建议连接项，不创建虚假结果。

---

### User Story 4 - 看懂对话中的执行过程 (Priority: P2)

作为使用者，我在一个连续的对话界面里既能看到助手回复，也能看到任务正在做什么、调用了哪类能力、是否等待确认、最终哪些步骤成功或失败，而不需要理解内部编排细节。

**Why this priority**: 对话与任务如果各自显示在不同界面，用户难以理解回答从何而来，也难以安全确认写操作。

**Independent Test**: 执行一次包含内置查询、MCP 查询和待确认写入的多轮会话，验证每轮消息、状态、确认卡片、结果和执行记录按时间顺序呈现且归属于正确任务。

**Acceptance Scenarios**:

1. **Given** 系统从聊天切换为任务执行，**When** 任务开始，**Then** 对话中显示简洁的当前步骤、所用能力类别、进度或阶段说明。
2. **Given** 同一会话有多个任务，**When** 用户查看历史，**Then** 每条结果、确认和执行记录都能对应到触发它的用户消息。
3. **Given** 任务仍在运行，**When** 用户继续发送不冲突的聊天消息，**Then** 系统可以回应而不丢失在途任务状态。
4. **Given** 新消息会改变正在等待确认的任务范围，**When** 用户提交该消息，**Then** 系统明确提示是修改原提案、放弃原提案还是创建新任务，不能静默混合。
5. **Given** 工具调用完成，**When** 系统生成最终回复，**Then** 回复区分已查询、已生成、待确认、已保存、失败和未处理，不把生成结果描述成已落库结果。

---

### User Story 5 - 在故障和重启后继续可信对话 (Priority: P3)

作为使用者，即使后台任务、模型或 MCP 能力失败，系统也会结束等待状态、给出可理解的错误，并在恢复后允许我从原会话重试，而不是永远显示“处理中”。

**Why this priority**: 当前入口已出现任务长期停留在 pending 的真实问题；对话化后消息与任务更多，必须保证失败可见且可恢复。

**Independent Test**: 在任务分派前、工具调用中和等待确认时分别模拟故障与进程重启，验证任务在限定时间内进入明确状态，原消息、范围、预览和已成功结果均可恢复。

**Acceptance Scenarios**:

1. **Given** 任一执行阶段出现未处理错误，**When** 后台执行终止，**Then** 对应任务进入明确失败或部分成功状态，并显示安全、可行动的错误说明。
2. **Given** 任务状态长时间没有变化，**When** 超过停滞阈值，**Then** 用户看到停滞提示和重试入口，不再无限显示处理中。
3. **Given** 系统在对话或任务执行期间重启，**When** 用户重新打开会话，**Then** 已保存消息、任务范围、确认状态和执行结果可以恢复。
4. **Given** 用户选择重试，**When** 已有步骤成功完成，**Then** 系统不重复产生相同外部影响，并优先从失败或未处理步骤继续。

### Edge Cases

- 用户只发送表情、空白、超长文本或无法识别的语言时，系统应提供简短引导，不创建无意义后台任务。
- 用户一句话包含多个彼此独立或相互冲突的任务时，系统应拆分安全的只读任务，或先确认优先级与写入范围。
- 会话引用的对象已被删除、修改或不再有权访问时，系统应刷新范围并说明变化，不使用陈旧数据执行写入。
- 多个能力名称相似、结果范围不同或需要不同权限时，系统应选择最小权限方案；若结果会明显不同则先询问用户。
- MCP 在发现后、调用前变为不可用时，系统应重新检查可用性并安全失败。
- 用户撤销或变更 MCP 授权后，后续消息不得沿用旧权限；已有审计记录仍保留但不暴露凭据。
- 外部结果包含恶意提示、伪造确认语句、链接或敏感数据时，不得借此触发额外工具调用或写操作。
- 用户快速重复发送相同任务时，系统应识别重复请求，避免重复写入或重复产生外部影响。

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 系统 MUST 在统一会话入口中区分普通对话、能力询问、需要澄清的请求和可执行任务。
- **FR-002**: 系统 MUST 对问候、感谢、告别和能力询问提供自然回应，且不得为纯聊天创建业务工具调用。
- **FR-003**: 系统 MUST 基于当前真实可用能力生成能力说明，说明内容随能力连接、可用性和用户权限变化而更新。
- **FR-004**: 系统 MUST 从自然语言中确定任务目标、对象范围、必要参数、风险和读写性质，不要求用户记忆固定命令或工具名。
- **FR-005**: 系统 MUST 在可以从当前消息和会话安全推断条件时直接继续，只在缺失条件会实质影响正确性或安全性时澄清。
- **FR-006**: 系统 MUST 将后续消息中的指代绑定到明确的历史对象范围；范围不唯一、已过期或已变化时必须先说明或澄清。
- **FR-007**: 系统 MUST 将每个可执行任务与触发消息、会话和使用的对象范围关联，使执行过程可恢复、可审计。
- **FR-008**: 系统 MUST 发现并评估当前用户可使用的内置能力和 MCP 能力，包括能力用途、读写性质、所需权限、可用状态和影响范围。
- **FR-009**: 系统 MUST 仅选择能够真实完成请求且当前可用、已授权的能力，不得调用未注册、离线或权限不足的能力。
- **FR-010**: 系统 MUST 在多个能力可选时优先采用数据范围最小、权限最少、外部影响最低的方案。
- **FR-011**: 系统 MUST 只向所选能力传递完成任务所需的最小数据，不得默认传递完整会话、无关正文、凭据或其他用户数据。
- **FR-012**: 系统 MUST 把能力返回内容视为不可信外部数据；返回内容不得修改权限、系统规则、确认状态或未经用户授权地触发后续操作。
- **FR-013**: 系统 MUST 对只读查询和分析允许直接执行，并显示来源和结果状态。
- **FR-014**: 系统 MUST 在任何内部或外部写操作前展示结构化预览，包含目标、影响数量、变更摘要、风险、可逆性和拟使用的能力。
- **FR-015**: 系统 MUST 只接受与待确认提案绑定的结构化批准或拒绝决定，不得用对话文本匹配替代确认。
- **FR-016**: 系统 MUST 在批准后重新检查对象归属、版本、能力可用性和权限；任一检查失败时不得静默覆盖或部分越权执行。
- **FR-017**: 系统 MUST 在对话中展示任务阶段、能力类别、进度、确认状态、结果摘要和失败原因，但不得展示隐藏推理、系统提示词或凭据。
- **FR-018**: 系统 MUST 区分已查询、已生成未保存、等待确认、已保存、失败和未处理结果。
- **FR-019**: 系统 MUST 为每次能力调用保留脱敏执行记录，至少包含触发消息、任务、能力、操作性质、参数摘要、结果规模、状态和耗时。
- **FR-020**: 系统 MUST 在没有可用能力时自然说明缺失项、可完成部分和可选下一步，不得编造数据或声称已执行。
- **FR-021**: 系统 MUST 在能力超时、离线或返回无效结果时保留已成功部分，清楚标识失败部分，并提供安全重试或替代方案。
- **FR-022**: 系统 MUST 将任何未处理执行异常转化为用户可见终态，不允许任务无限保持等待或运行状态。
- **FR-023**: 系统 MUST 检测长期无进展任务，并向用户提供停滞说明和不会重复外部影响的重试操作。
- **FR-024**: 系统 MUST 在重启后恢复会话消息、任务范围、执行状态、待确认提案和已完成结果。
- **FR-025**: 系统 MUST 隔离不同用户的会话、能力、任务、结果和审计记录；用户权限撤销后不得继续使用旧授权。
- **FR-026**: 系统 MUST 对重复消息和重试实施幂等保护，避免重复写入或重复外部影响。

### Key Entities

- **Conversation**: 一段连续交互的边界，关联所有参与消息、当前上下文范围、在途任务和最近活动时间。
- **Conversation Message**: 用户或助手的一次可恢复消息，记录发送者、正文、时间、与任务或确认提案的关联，以及呈现状态。
- **Routing Decision**: 对一条用户消息的可审计判断，描述其属于聊天、能力询问、澄清或任务，以及确定的目标、范围和读写性质；不保存隐藏推理。
- **Capability**: 当前可发现的内置或 MCP 能力，描述用途、操作性质、权限需求、可用性和风险属性，不包含凭据。
- **Task**: 从一条或多条会话消息产生的持久化工作，关联对象范围、执行状态、结果和重试信息。
- **Confirmation Proposal**: 在产生写入或外部影响前展示给用户的结构化提案，关联确定的任务、目标、预览、风险、决定和过期状态。
- **Execution Record**: 一次能力调用或执行步骤的脱敏记录，用于还原事实过程、结果和失败位置。

### Data Safety & AI Control *(mandatory when the feature stores content or uses AI)*

- **Durable acceptance point**: 用户消息在系统确认接收前必须持久保存；可执行任务在任何模型判断或能力调用前必须与触发消息、对象范围和任务状态一并持久保存。
- **AI authority boundary**: AI 可以回应聊天、识别任务、选择已授权能力、执行只读查询并生成提案；任何创建、修改、删除、发布、发送或其他外部影响都必须通过与具体提案绑定的结构化确认。
- **Failure fallback**: 对话历史、原始用户数据、已成功结果和待确认提案在模型、后台执行或 MCP 失败时仍可查看；失败必须进入明确终态并支持安全重试。
- **Privacy and ownership**: 会话、任务、能力授权、结果和执行记录默认仅归属当前用户；只向能力披露完成当前任务所需的最小数据，并在所有边界重新校验权限。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 问候、感谢、告别和能力询问测试集中至少 95% 获得自然对话回复，且 100% 不产生业务写入或错误式能力缺口。
- **SC-002**: 对现有支持任务的至少 30 种自然表达变体，任务目标、对象范围和读写性质识别准确率达到 90% 以上。
- **SC-003**: 条件完整的只读请求中至少 95% 无需额外澄清即可开始执行；条件不足的请求平均只提出一个必要问题。
- **SC-004**: 多轮测试中，“这些”“刚才的”等明确指代与上一轮对象范围一致率达到 100%，且不会意外扩大范围。
- **SC-005**: 在已连接能力覆盖请求的测试集中，正确选择内置或 MCP 能力的比例达到 95%，无权限能力调用次数为 0。
- **SC-006**: 所有写入和外部影响测试在结构化批准前业务状态变化为 0；批准后仍有所有权或版本冲突的请求静默覆盖次数为 0。
- **SC-007**: 任务开始后，用户在 2 秒内看到首次状态或阶段反馈；普通聊天回复的 95% 在 3 秒内开始呈现。
- **SC-008**: 对后台异常、能力离线、超时和进程重启的故障测试，100% 的任务在规定停滞窗口内进入明确终态或显示可操作的停滞提示，不出现无限处理中。
- **SC-009**: 执行记录安全扫描中凭据、认证头、隐藏提示和跨用户数据泄漏次数为 0。
- **SC-010**: 首次使用者无需阅读命令列表即可通过对话完成“查询一批对象并对其执行后续分析”的比例达到 85% 以上。

## Assumptions

- 首个版本面向现有已登录个人用户，不开放匿名对话或多人共享会话。
- 现有自助 Agent 的任务持久化、状态展示、执行记录和写入确认规则继续作为底层安全边界。
- 普通聊天以简洁、任务导向的助手体验为主，不以开放域陪聊或长期人格记忆为目标。
- MCP 能力必须由管理员或用户事先连接并授权；本功能不会在对话中自动安装连接器、保存新凭据或提升权限。
- 第一个版本支持一个用户在同一会话中存在多个任务，但不会让相互依赖的写任务在未经确认的情况下自动并行。
- 对话上下文以完成当前及后续任务所需的对象、条件、决定和结果为主，不默认把完整历史发送给每个能力。
- 现有领域规则继续决定最终写入是否合法；Agent 的意图判断或用户批准都不能绕过这些规则。
