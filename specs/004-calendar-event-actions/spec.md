# Feature Specification: 日历事件快捷操作与视觉优化

**Feature Branch**: `004-calendar-event-actions`

**Created**: 2026-07-27

**Status**: Draft

**Input**: User description: "优化日历模块：左键单击或移动端轻点事件后弹出操作 popover，可标记已完成、设为重要并在事件前 4 小时发送邮件提醒、添加备注并分多批上传多张图片且持久化文件关联；完成事件显示 emoji，重要事件使用柔和红色背景，已流逝时间区域灰化但文字清晰；已有事件优先显示名称，时间段显示在下方。"

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 快速调整事件状态 (Priority: P1)

作为个人用户，我希望在桌面端左键单击或在移动端轻点日历事件后，直接在弹出的操作面板中切换完成状态或重要状态，以便无需离开日历就能更新事件。

**Why this priority**: 状态调整是本次优化的核心入口，并直接决定完成标记、重要样式和邮件提醒是否生效。

**Independent Test**: 分别在桌面端和移动端打开一个已有事件，通过操作面板将其标为已完成和重要，再取消两个状态；验证状态、视觉标记和提醒计划随每次操作正确变化。

**Acceptance Scenarios**:

1. **Given** 用户在桌面端查看一个有权编辑的日历事件，**When** 用户左键单击该事件，**Then** 事件附近显示操作面板，且面板提供“已完成”“设为重要”和“添加备注”操作。
2. **Given** 用户在移动端查看一个有权编辑的日历事件，**When** 用户轻点该事件，**Then** 屏幕可见区域内显示同等功能的操作面板。
3. **Given** 一个未完成事件的操作面板已打开，**When** 用户选择“已完成”，**Then** 完成状态被保存，当前日历立即显示完成 emoji 标记，重新打开页面后标记仍然存在。
4. **Given** 一个已完成事件的操作面板已打开，**When** 用户取消完成状态，**Then** 完成状态被保存且完成 emoji 标记消失。
5. **Given** 一个具有未来开始时间且尚未设为重要的事件，**When** 用户选择“设为重要”，**Then** 重要状态被保存，事件显示柔和红色背景，并建立事件开始前 4 小时的邮件提醒。
6. **Given** 一个已设为重要且提醒尚未发送的事件，**When** 用户取消重要状态，**Then** 重要样式被移除且未发送的 4 小时邮件提醒被取消。
7. **Given** 一个事件同时为已完成和重要，**When** 用户查看日历，**Then** 完成 emoji 与重要背景同时清晰可见，且事件文字仍可辨认。

### User Story 2 - 为事件添加图文备注 (Priority: P2)

作为个人用户，我希望从事件操作面板添加文字备注，并可分多批选择和上传多张图片，以便把与事件相关的记录长期保存在同一事件下。

**Why this priority**: 图文备注扩展了日历事件的信息承载能力，且图片与事件的可靠关联是明确的数据要求。

**Independent Test**: 为一个已有事件添加文字备注，连续三次追加选择多张图片；保存并重新打开该事件，验证文字和所有成功上传的图片均存在且只归属于该用户的该事件备注。

**Acceptance Scenarios**:

1. **Given** 事件操作面板已打开，**When** 用户选择“添加备注”，**Then** 用户可输入备注文字并选择一张或多张图片。
2. **Given** 用户已选择一批图片，**When** 该批图片上传成功后用户再次选择另一批图片，**Then** 新图片被追加到同一事件备注，先前图片不会被替换。
3. **Given** 备注文字和图片均已成功保存，**When** 用户关闭后重新打开该事件备注，**Then** 系统展示原备注及全部关联图片。
4. **Given** 一批图片中部分文件上传失败，**When** 本次保存结束，**Then** 已成功保存的备注和图片保持可用，失败文件被逐项指出且可以重试，不产生无法识别归属的图片记录。
5. **Given** 用户查看其他用户无权共享给自己的事件，**When** 用户尝试访问其备注或图片，**Then** 系统不展示或允许修改这些内容。

### User Story 3 - 清晰识别事件与已流逝时间 (Priority: P3)

作为个人用户，我希望日历优先呈现事件名称，将时间段放在名称下方，并用不干扰文字阅读的灰色区分已流逝时间，以便快速扫描日程和判断当前进度。

**Why this priority**: 该视觉层级提升浏览效率，但不阻塞事件状态和备注的核心操作。

**Independent Test**: 在包含过去、当前和未来时段，以及普通、完成、重要事件的日历中检查桌面端和移动端展示；确认名称优先、时间位于下方、过去区域灰化且所有文字清晰。

**Acceptance Scenarios**:

1. **Given** 一个已有且已排期的事件，**When** 日历显示该事件，**Then** 事件名称作为首要内容展示，时间段展示在名称下方。
2. **Given** 日历包含已经流逝的时间区域，**When** 用户查看日历网格，**Then** 已流逝区域使用灰色背景与当前或未来区域区分，且区域内文字仍满足清晰阅读要求。
3. **Given** 已流逝区域中存在重要事件，**When** 用户查看该事件，**Then** 网格灰色背景不会覆盖事件的柔和红色重要样式或降低事件文字可读性。
4. **Given** 事件名称较长或移动端空间有限，**When** 事件卡片无法展示全部内容，**Then** 名称仍优先于时间段，且用户可通过打开操作面板识别所选事件。

### Edge Cases

- 当事件没有明确开始时间时，用户仍可设置重要状态，但系统必须说明无法安排“开始前 4 小时”邮件提醒，直至事件获得开始时间。
- 当事件距开始不足 4 小时才被设为重要时，系统为仍未开始的事件安排一次尽快发送的邮件，不补发已经开始或结束事件的提醒。
- 当重要事件的开始时间被修改时，尚未发送的邮件提醒随新的开始时间调整；重复保存或重试不得造成重复邮件。
- 当发信能力未配置或暂时不可用时，重要状态和视觉样式仍须保存，并向用户明确显示邮件提醒未正常可用或发送失败。
- 当备注为空但包含图片时，允许保存；当备注文字与图片都为空时，不创建空备注。
- 当用户分多批上传图片、重复选择同一文件或单个文件不符合现有图片限制时，系统逐项反馈结果，且不破坏已保存内容。
- 当事件同时处于已完成、重要和已流逝区域时，各视觉含义须能共存，事件名称和时间仍保持可读。
- 已流逝区域的判断遵循用户当前时区；当前时间边界变化后，日历应更新过去与未来区域的划分。
- 操作面板不得超出移动端可见区域；点击或轻点面板外部可关闭面板，且未提交的编辑不得被误保存。

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 系统 MUST 在桌面端左键单击日历事件、移动端轻点日历事件时打开该事件的操作面板。
- **FR-002**: 操作面板 MUST 清楚展示事件当前的完成和重要状态，并提供“已完成”“设为重要”和“添加备注”操作；已生效的可切换状态 MUST 支持从同一入口取消。
- **FR-003**: 系统 MUST 持久保存完成状态，并在操作成功后立即更新当前日历中的事件表现。
- **FR-004**: 已完成事件 MUST 显示明确的完成 emoji；该标记 MUST 与事件名称保持可区分，且不能仅依赖颜色表达完成状态。
- **FR-005**: 系统 MUST 持久保存重要状态；重要事件 MUST 使用克制、柔和的红色背景，并保持文字与其他状态标记清晰可见。
- **FR-006**: 对具有未来开始时间的重要事件，系统 MUST 安排一封在事件开始前 4 小时触发的邮件提醒。
- **FR-007**: 重要状态或事件开始时间发生变化时，系统 MUST 相应创建、调整或取消尚未发送的 4 小时邮件提醒，并防止同一事件同一提醒时点重复发送。
- **FR-008**: 对距开始不足 4 小时才设为重要的未开始事件，系统 MUST 安排一次尽快发送的邮件；对已经开始或结束的事件 MUST 不补发历史提醒。
- **FR-009**: 当邮件提醒无法安排或发送时，系统 MUST 保留事件的重要状态，并向用户提供可理解的提醒状态或失败信息。
- **FR-010**: 用户 MUST 能从操作面板创建或编辑该事件的文字备注，且文字备注在明确保存成功后可再次打开查看。
- **FR-011**: 同一事件备注 MUST 支持在一次选择中添加多张图片，并支持通过多次选择分批追加图片；后续批次 MUST 不覆盖先前已保存图片。
- **FR-012**: 系统 MUST 在持久化业务数据中建立事件、备注与每个图片文件之间的明确关联，使每张图片均可追溯到所属用户、所属事件和所属备注。
- **FR-013**: 图片关联 MUST 仅在相应图片已成功保存后生效；部分上传失败 MUST 不回滚已成功保存的备注或其他图片，并 MUST 支持用户识别和重试失败项。
- **FR-014**: 备注和关联图片 MUST 默认为私有，仅允许事件所属用户或既有授权规则允许的用户查看和修改。
- **FR-015**: 日历 MUST 将当前时间之前的已流逝时间区域显示为灰色背景，并确保网格标签、事件名称、时间段、emoji 和操作状态仍清晰可读。
- **FR-016**: 已流逝区域的背景 MUST 作为时间网格层级的视觉提示，不得覆盖重要事件的柔和红色背景或完成标记。
- **FR-017**: 对已有的已排期事件，日历 MUST 优先展示事件名称，并将时间段展示在名称下方；在空间受限时也 MUST 保持这一信息优先级。
- **FR-018**: 操作面板 MUST 在桌面端和移动端可完整操作，保持在可见区域内，并支持通过面板外操作关闭。
- **FR-019**: 状态、提醒、备注或图片操作失败时，系统 MUST 明确指出未保存的内容，不得以成功外观掩盖失败，也不得破坏该事件此前已保存的数据。

### Scope Boundaries

- 本功能只优化现有日历事件的操作入口、状态、提醒、备注附件关联和视觉展示。
- 本功能不新增日历视图类型，不改变现有拖拽、调整时长、冲突检测或 Todo 与日历同步规则。
- 本功能不新增重复事件编辑语义；重复事件继续遵循系统既有的单次与系列处理规则。
- 本功能不包含外部日历双向同步、浏览器推送提醒、图片分析或 AI 自动生成备注。

### Key Entities *(include if feature involves data)*

- **Calendar Event**: 用户在日历中查看和操作的事件，包含名称、开始与结束时间、完成状态、重要状态、所属用户及既有排期属性。
- **Event Note**: 归属于一个日历事件的用户备注，包含文字内容、保存状态和所属用户，可关联零张或多张图片。
- **Media Asset**: 用户上传并成功保存的图片文件及其基础信息，可通过明确关联归属于一个事件备注。
- **Event Note Media Association**: 表达事件备注与图片文件的持久关系，确保图片可追溯到所属用户、事件和备注，并支持分批追加。
- **Email Reminder**: 由重要事件派生的邮件提醒，包含目标事件、计划发送时间、发送状态及防重复标识，并随重要状态和事件时间变化而调整。

### Data Safety & AI Control *(mandatory when the feature stores content or uses AI)*

- **Durable acceptance point**: 状态或备注在业务记录成功保存后才视为完成；每张图片仅在文件保存成功且与所属备注、事件的关联同时持久化后才视为已接受。界面必须区分已保存项与失败项。
- **AI authority boundary**: 本功能不引入 AI 行为；AI 不得代替用户更改完成状态、重要状态、备注、图片或邮件提醒。
- **Failure fallback**: 邮件、图片上传或其他后台能力失败时，既有事件及此前已保存的状态、备注和图片仍可浏览与手工管理；失败项可单独重试。
- **Privacy and ownership**: 事件备注和图片默认私有，所有读取、修改和文件访问均沿用事件所有权与既有授权边界，不能通过文件标识绕过权限。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 在桌面端和移动端可用性测试中，至少 90% 的用户能在 5 秒内从日历事件完成一次状态切换，且无需离开日历页面。
- **SC-002**: 在发信能力正常且事件提前至少 4 小时设为重要的验收样本中，100% 的事件只产生一项计划于开始前 4 小时的邮件提醒，且至少 95% 的提醒在计划时点后 60 秒内开始发送。
- **SC-003**: 对状态切换、取消状态和修改事件时间的全部验收场景，提醒计划与最终事件状态一致，且不出现重复提醒。
- **SC-004**: 用户可对同一备注连续完成至少 3 批、合计至少 12 张有效图片的追加保存；重新打开事件后，100% 成功上传的图片仍与正确的事件备注关联。
- **SC-005**: 在覆盖桌面端和移动端的视觉验收样本中，100% 的完成、重要、已流逝及组合状态均可被正确识别，且事件名称和时间段保持可读。
- **SC-006**: 对所有已有已排期事件的验收样本，事件名称均先于时间段展示，时间段均位于名称下方。
- **SC-007**: 在模拟单张图片失败、邮件不可用和状态保存失败的验收中，100% 的既有已保存内容不丢失，并向用户明确指出失败项。

## Assumptions

- “多组图片”解释为：同一事件备注允许分多次选择图片，每次可选择多张，后续批次以追加方式保存。
- 已完成和重要均为可撤销状态，以满足用户“调整状态”的需求。
- 已流逝时间指用户当前时区下、当前时刻之前的日历时间网格区域，而不是将所有过去事件本身统一改成灰色。
- 对不足 4 小时才设为重要的未来事件采用“尽快发送一次”作为合理默认；已经开始或结束的事件不补发邮件。
- 邮件提醒依赖部署者已配置可用的发信能力；未配置时仍保存重要状态并向用户显示提醒不可用。
- 图片类型、大小、数量上限和删除规则沿用系统现有媒体安全与保留策略，本功能不重新定义这些全局规则。
- 事件名称、时间范围、用户时区、所有权和重复事件语义复用现有日历数据与规则。
